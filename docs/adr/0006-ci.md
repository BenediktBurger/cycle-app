# ADR-0006: Automated verification — local testing AND GitHub Actions CI (analyze + test + build web)

- **Date:** 2026-09-15
- **Status:** Accepted

## Context

Code is partly hand-written without continuous compile verification, and
local environments drift over time — SDK versions move, editor state
changes, and coding-agent sandboxes impose odd restrictions on what can
actually run. Neither local testing alone nor CI alone catches everything:
local runs are fast and interactive but happen on a possibly-diverged
machine; CI runs on a clean, reproducible machine but is slower and not
interactive.

Requirements: run `flutter analyze`, `flutter test`, and at least one real
build; cheap to run on every push; no platform signing or secrets needed;
and a fast feedback loop for the developer before anything is pushed.

## Decision

Automated verification happens **both locally and in CI**, as two layers of
the same loop:

**1. Local testing is the primary, fast feedback loop.** In the developer's
normal terminal (outside any sandbox), before every push:

```sh
flutter analyze
flutter test
flutter build web
```

These MUST be run before pushing — pushing is not an alternative to
local testing.

**2. GitHub Actions CI is the clean-machine backstop.** Workflow
`.github/workflows/ci.yml`:

- Runs on `ubuntu-latest`.
- Flutter **stable** via `subosito/flutter-action`.
- Steps: `flutter pub get` → `flutter analyze` → `flutter test` →
  `flutter build web`.
- Triggers: `push` to `main`, `pull_request` targeting `main`, and
  `workflow_dispatch` for manual convenience.

CI additionally validates every push and PR on a clean machine — explicitly
valuable **because local environments drift** (SDK versions, editor state,
sandbox quirks): CI verifies the code with a known-good stable SDK,
independent of whatever state the developer's host is in.

Former environment quirk (resolved 2026-09-16): an earlier omac
coding-agent sandbox denied `bind()` on loopback ports, which broke
`flutter_tester` (it requires a temporary loopback WebSocket server
socket), so local test runs had to happen outside the sandbox. That
restriction was lifted; `flutter pub get` followed by `flutter test` now
runs directly in agents' and developers' terminals alike.

## Consequences

- Every push to main and every PR gets analyzed, tested, and actually
  compiled (web build) on a clean machine, which catches the
  hand-written-code risk independent of local drift.
- Local runs catch most breakage in seconds-to-minutes without waiting
  for a CI round trip; CI then independently confirms it on stable SDK +
  ubuntu — two chances to catch a divergence between the two
  environments.
- Web as the only built target keeps it fast (locally and in CI); Android/iOS
  builds are a local concern (and later, optionally, a release workflow) —
  not needed to validate code correctness.
- CI uses current stable Flutter; the pinned/intl-version caveat (pubspec
  comment) is coordinated with the developer's local SDK so the two
  environments should stay in lockstep — if CI and local diverge badly, that
  is a signal to pin the Flutter version explicitly in `flutter-version:` of
  the action.
- No test coverage/artifact uploads initially (keep it boring); can be added
  later without changing the decision.
