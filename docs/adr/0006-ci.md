# ADR-0006: Automated verification — local testing AND GitHub Actions CI (analyze + format + test + build web + Android debug)

- **Date:** 2026-09-15
- **Status:** Accepted
  (amended in place, 2026-09: dart format gate, Flutter pin, Android debug
  build, `development` triggers; the release pipeline (an unsigned CI
  build, signed locally, triggered by release-branch pushes — see the
  amendments there) is a decision of [ADR-0009](0009-release-pipeline-and-signing.md))

## Context

Code is partly hand-written without continuous compile verification, and
local environments drift over time — SDK versions move, editor state
changes, and coding-agent sandboxes impose odd restrictions on what can
actually run. Neither local testing alone nor CI alone catches everything:
local runs are fast and interactive but happen on a possibly-diverged
machine; CI runs on a clean, reproducible machine but is slower and not
interactive.

Requirements: run `flutter analyze`, `dart format --set-exit-if-changed`,
`flutter test`, and at least one real build; cheap to run on every push; no
platform signing or secrets needed; and a fast feedback loop for the
developer before anything is pushed.

## Decision

Automated verification happens **both locally and in CI**, as two layers of
the same loop:

**1. Local testing is the primary, fast feedback loop.** In the developer's
normal terminal (outside any sandbox), before every push:

```sh
flutter analyze
flutter test
flutter build web
```

These MUST be run before pushing — pushing is not an alternative to
local testing.

**2. GitHub Actions CI is the clean-machine backstop.** Workflow
`.github/workflows/ci.yml`:

- Runs on `ubuntu-latest`.
- Flutter **stable**, pinned via the committed `tool/flutter-version`
  file — both CI workflows (CI and Release) read that file directly with
  the same parse the F-Droid build recipe uses, and the dev machine's SDK
  is kept at the pinned version.
- Steps: `flutter pub get` → `flutter analyze` →
  `dart format --output=none --set-exit-if-changed .` (strict, mirrors the
  local doc gate) → `flutter test` → `flutter build web` →
  `flutter build apk --debug` (unsigned; Android SDK licenses accepted in a
  preceding step).
- Triggers: `push` to `development` (primary integration line) and `main`
  (release line), `pull_request` targeting either, and `workflow_dispatch`
  for manual convenience. Superseded runs of the same branch are cancelled
  via a concurrency group.

CI additionally validates every push and PR on a clean machine — explicitly
valuable **because local environments drift** (SDK versions, editor state,
sandbox quirks): CI verifies the code with a known-good stable SDK,
independent of whatever state the developer's host is in.

Former environment quirk (resolved 2026-09-16): an earlier omac
coding-agent sandbox denied `bind()` on loopback ports, which broke
`flutter_tester` (it requires a temporary loopback WebSocket server
socket), so local test runs had to happen outside the sandbox. That
restriction was lifted; `flutter pub get` followed by `flutter test` now
runs directly in agents' and developers' terminals alike.

## Consequences

- Every push to `development` and to `main`, and every PR targeting either,
  gets analyzed, format-checked, tested, and actually compiled (web build
  plus an Android debug build) on a clean machine, which catches the
  hand-written-code risk independent of local drift.
- Local runs catch most breakage in seconds-to-minutes without waiting
  for a CI round trip; CI then independently confirms it on stable SDK +
  ubuntu — two chances to catch a divergence between the two
  environments.
- The web build stays the local correctness gate: it is what runs locally
  day to day. CI additionally compiles the Android target (debug,
  unsigned) because Android is the upcoming product target
  ([ADR-0009](0009-release-pipeline-and-signing.md)) and the local Android
  toolchain is not yet green (setup now in
  [CONTRIBUTING.md](../../CONTRIBUTING.md), "Android toolchain"; was
  release.md Phase A) — surface Android breakage during
  integration now instead of wait-for-toolchain-then-discover.
- The dart format check is a CI gate and is mirrored locally (apart from
  being part of the local full gate below, it is documented in
  CONTRIBUTING.md and AGENTS.md); formatting is fixed with a plain
  `dart format .` before pushing, never negotiated in CI.
- CI uses stable Flutter, pinned via `tool/flutter-version` (both CI
  workflows read that file directly — same file, same parse as the
  F-Droid build recipe; a Flutter bump edits that one file); the
  pinned/intl-version caveat (pubspec comment) is coordinated with the
  developer's local SDK so the two environments stay in lockstep — the
  pin file is kept matching the local SDK.
- No test coverage/artifact uploads initially (keep it boring); can be added
  later without changing the decision.
