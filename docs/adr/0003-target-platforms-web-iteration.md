# ADR-0003: Web/Chrome as iteration target; Android + iOS as product targets

- **Date:** 2026-09-15
- **Status:** Accepted

## Context

The product is a mobile app for **Android + iOS**. During development, though,
we need a fast iteration/test loop (start app, add data, inspect behavior)
without depending on Android Studio/Xcode toolchains or emulators. Flutter web
running in Chrome gives exactly that for this app's needs, with a much lighter
toolchain. Additionally, a PWA is a cheap bonus later.

Platform constraints: some Flutter packages are Android-only or
otherwise native-only. Using such packages in code shared across platforms
would break the web iteration loop, or force plugin Availability checks
everywhere.

## Decision

- The **product targets Android + iOS**. A PWA is a welcome bonus.
- **Web/Chrome is the iteration and test target** during development; CI also
  builds for web (`flutter build web`) as the lightest compile check.
- **No Android-only plugins in core code.** Any dependency that does not work
  on web must be isolated behind platform-guarded conditional imports, or
  confined to a clearly separated feature layer — never imported from core
  UI/domain code.
- Platform folders for Android/iOS are generated by the user locally
  (`flutter create --platforms=android,ios …`, see CONTRIBUTING.md); the web
  shell (`web/index.html`, `web/manifest.json`) is hand-written and kept
  minimal.

## Consequences

- Fast local iteration (`flutter run -d chrome`) without a mobile toolchain;
  CI's first real compile check is a web build, which is cheap and stable.
- Package selection is constrained: dependencies must work on web (or be
  cleanly isolated). Examples honored in other ADRs: drift uses
  `WasmDatabase` on web; `flutter_secure_storage` (native later) and
  `sqlcipher_flutter_libs` (native later) must never leak into shared code —
  web gets a PIN lock only (see ADR-0005).
- The web iteration path requires drift's `sqlite3.wasm` + worker assets to be
  available for the web build (documented separately when the DB lands).
- Platform feature parity is asymmetric: features that work only on native
  (SQLCipher, biometric lock) are "optional/native-later" by design, not
  regressions of web.
